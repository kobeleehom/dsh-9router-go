feat: manage a ZCode proxy sidecar and publish its models

A ZCode (Z.ai) account is not an OpenAI-compatible endpoint, so the gateway
could not reach one. This adds a second managed sidecar that republishes the
account and registers it back into the gateway as a custom provider, keeping
the ZCode models addressable by the gateway's own combos and fallbacks.

The proxy is fetched and prepared automatically: the pinned zcode2api release
is downloaded, its SHA-256 and native header are verified, the captcha solver
its dependencies are installed once, and the result is reused thereafter.
`autoInstall: false` plus an absolute `executable` opts out for operators who
would rather not run a third-party binary that publishes no license.

Three upstream behaviours shaped the implementation and are worth recording:

- The gateway's connection create and update routes take the credential
  differently. Create reads a top-level `apiKey`; update reads the merged
  `data` map and ignores that field, so an update carrying only `apiKey`
  reports success while the old credential stays in place. The update payload
  therefore carries both forms.
- The proxy persists its password in SQLite and lets the stored value win over
  `.env`, so the configured token is pushed through its settings API on every
  activation, with `legacyAuthTokens` covering a value already stored.
- The gateway lists custom models from its own store and never probes a custom
  node's `/v1/models`, so the node stays invisible until each model is
  registered against it.

Registration order matters for the same reason: the node is written before the
DSH route is published, otherwise the advertised catalog would omit ZCode.
